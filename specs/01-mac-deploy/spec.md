## 问题陈述

这个项目已经在 Windows 环境中跑过，但 macOS 环境下的可运行性还没有被明确记录为一个实施目标。当前最重要的事情不是立刻决定最终的打包和分发技术选型，而是先让项目能在开发者自己的 Mac 上稳定开发运行，并记录后续面向普通 Mac 用户分发时还需要补齐哪些工作。

用户也需要明确：macOS 是否支持与 Windows 环境类似的核心剪贴板能力。当前产品范围是文本剪贴板历史、文本复制回填、置顶、删除、清空和本地持久化。这些能力应纳入本次 macOS 开发可运行性 spec 的验收范围。

## 解决方案

为现有的 Electron、Vue、TypeScript、Vite 桌面应用建立 macOS 开发可运行性。

本 spec 需要验证应用可以在 macOS 上安装依赖、成功构建、以开发模式启动、读取 macOS 文本剪贴板、写回 macOS 文本剪贴板，并在应用重启后保留本地剪贴板历史。

本 spec 还需要产出后续 macOS 分发改造清单，但不要求在本次实施中完成分发能力。分发相关主题包括 `.app` 或 `.dmg` 打包、签名、公证、自动更新、开机启动、托盘或菜单栏行为，以及面向用户的权限说明。

## 用户故事

1. 作为开发者，我希望能在 macOS 上安装项目依赖，以便我可以在自己的 Mac 环境中开发这个项目。
2. 作为开发者，我希望项目能在 macOS 上构建成功，以便确认源码和构建配置不是 Windows-only。
3. 作为开发者，我希望 Electron 应用能在 macOS 开发模式下启动，以便我可以手动测试桌面端体验。
4. 作为开发者，我希望渲染层 UI 能在 macOS 上正常加载，以便我可以使用与 Windows 环境一致的界面。
5. 作为开发者，我希望应用能读取从其他 macOS 应用复制的文本，以便剪贴板历史能覆盖日常本地使用场景。
6. 作为开发者，我希望应用忽略空文本或纯空白文本，以便历史列表保持有用。
7. 作为开发者，我希望重复复制相同文本时更新已有历史项，而不是新增重复记录，以便列表不会被重复内容污染。
8. 作为开发者，我希望复制过的文本能在 macOS 上本地持久化，以便应用重启后仍能恢复历史记录。
9. 作为开发者，我希望置顶项能在 macOS 上保持可用，以便重要片段不会被普通历史清理规则移除。
10. 作为开发者，我希望未置顶的普通历史项在 macOS 上继续遵守现有数量上限，以便本地存储不会无限增长。
11. 作为开发者，我希望能把历史项重新复制回 macOS 系统剪贴板，以便我可以复用之前复制过的内容。
12. 作为开发者，我希望应用避免把自己写回剪贴板的文本立刻再次采集进历史，以便复制回填不会制造噪声更新。
13. 作为开发者，我希望能在 macOS 上删除单条历史记录，以便移除不需要的条目。
14. 作为开发者，我希望能在 macOS 上清空未置顶的普通历史，以便清理列表时保留置顶内容。
15. 作为开发者，我希望文本转换结果的复制动作能在 macOS 上工作，以便转换后的内容可以粘贴到其他应用。
16. 作为开发者，我希望保留符合 macOS 习惯的应用生命周期行为，以便关闭最后一个窗口时应用不会意外退出。
17. 作为开发者，我希望记录 macOS 本地环境搭建中的已知坑，以便依赖安装和 Electron 二进制下载问题更容易恢复。
18. 作为开发者，我希望明确记录“更深层的 macOS 剪贴板兼容”应该放在当前 spec 还是后续 spec，以便本次范围不会失控。
19. 作为开发者，我希望产出后续 macOS 分发改造清单，以便未来打包发布工作有清晰起点。
20. 作为开发者，我希望未定的平台技术决策被明确标为非本次范围，以便开发可运行性可以先落地。

## 实施决策

- 将本 spec 定义为 macOS 开发可运行性 spec，而不是 macOS 公开分发 spec。
- 保持当前 Electron clipboard API 路径作为文本剪贴板读写方案。macOS 支持这类基于 Electron 的文本剪贴板能力，因此当前剪贴板历史 MVP 应归入本 spec。
- 将当前文本剪贴板行为作为兼容目标。文本历史、复制回填、置顶、删除、清空、去重、空文本过滤和持久化都需要在 macOS 上验证。
- 除非测试发现现有剪贴板历史服务无法处理的具体 macOS 平台差异，否则不引入 Windows/macOS 抽象层。
- 使用现有主进程剪贴板历史服务作为剪贴板可运行性的主要行为边界。
- 使用现有 preload IPC 暴露面作为渲染层与主进程之间的集成边界。
- 使用现有渲染层面板作为剪贴板历史和文本转换复制行为的手动验证入口。
- 记录 macOS 依赖安装指引，包括在网络受限或下载较慢时 Electron 二进制可能需要配置镜像。
- 将本地开发验证命令纳入本 spec 的交付结果。
- 记录后续 macOS 分发改造清单，但本 spec 不实施应用打包、签名、公证、自动更新或安装器体验。
- 如果未来需要超出文本剪贴板的 Windows/macOS 深度对齐，应在本 spec 之后新建 spec。示例包括图片剪贴板历史、文件剪贴板历史、富文本或 HTML 剪贴板历史、全局快捷键、托盘常驻、开机启动注册，以及生产级 macOS 安装包行为。

## 测试决策

- 优先测试外部行为，而不是实现细节。测试应断言剪贴板历史服务对外表现，而不是内部定时器或数组的具体实现。
- 最高价值的测试边界是剪贴板历史服务边界。测试应覆盖初始化、采集行为、去重、置顶、删除、清空、复制回填忽略逻辑和持久化。
- 集成验证应覆盖从渲染层意图到主进程剪贴板行为的 IPC 链路。
- macOS 手动验证应确认：从其他 macOS 应用复制文本后，该文本会出现在历史中；从历史中复制某条记录后，可以粘贴到其他应用。
- 构建验证应包括 TypeScript 检查和 Electron/Vite 构建。
- 开发可运行性验证应包括 Electron 二进制安装成功后，在 macOS 上启动开发态应用。
- 当前代码库主要已有手动验证和构建验证经验；在扩展平台特定行为前，可能需要补充聚焦的自动化测试。

## 非本次范围

- 面向普通用户的 macOS 公开分发。
- `.app` 或 `.dmg` 打包。
- Apple Developer ID 签名。
- Apple 公证。
- 自动更新。
- 开机启动或登录项能力。
- 托盘常驻或菜单栏常驻。
- 全局快捷键。
- 图片、文件、HTML、RTF 或其他非文本格式的剪贴板历史。
- Windows-specific 重写。
- 完整跨平台剪贴板适配层，除非实施过程中发现具体 macOS 不兼容问题。

## 进一步说明

当前代码检查没有发现明显的 Windows-only API。应用基于 Electron clipboard API 实现剪贴板能力，并且已经包含符合 macOS 习惯的窗口生命周期分支。

当前 macOS 验证在依赖准备后已成功完成生产构建。开发态启动被本地 Electron 二进制安装不完整阻断，这是环境搭建问题，需要在本 spec 中记录并解决。

针对“macOS 剪贴板支持应放在当前 spec 还是新建 spec02”的问题：当前文本剪贴板能力放在本 spec 中。只有超出当前文本剪贴板 MVP 的深度平台能力，或生产级 macOS 分发打包能力，才新建后续 spec。
