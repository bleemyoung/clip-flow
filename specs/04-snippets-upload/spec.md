# 04 Snippets 手动上云需求（草案）

状态：已实施；macOS 关键链路与自动化验收通过，Windows 尚未验证。实际结果见 [验收记录](./acceptance.md)。与 05 保持独立，执行顺序为“05 另存为 Snippet → 04 手动上云”。

## 实施顺序（强制）

- 必须先实现并通过 [05 Clipboard 另存为 Snippet](../05-clipboard-save-as-snippet/spec.md) 的验收，再开始本 spec 的代码实施；不得并行实施 04、05。
- 开始 04 前，先核对 05 的验收记录。记录须包含实际验证系统、结果和未验证项目；缺少验收记录或必需验收项未通过时，继续完成 05，不得推断其已完成。
- spec 编号用于标识，不代表执行先后。不得因为 `04` 小于 `05` 而优先实施本 spec。
- 本功能仍支持直接在 Snippets 新建的片段；这一功能独立性不豁免上述实施顺序。

## 原需求依据

- `../02-snippets-local/spec.md` 的“实施决策”规定：“Snippets 是离线、单用户的桌面端功能；本次不连接 Java 后端、数据库或任何远端 API。”这是离线 V1 的阶段范围。
- `../03-java-snippets-backend/requirements.md` 的“边界”规定：“本阶段不替换 Electron 离线 Snippets 的数据来源，不移除现有本地功能。”
- 同一文档的“Snippets API”已定义 `POST /api/snippets` 创建接口，并明确允许重复标题与内容；“边界”暂不包含后端编辑、删除和云端部署。
- 本需求新增桌面端手动创建、关联和更新后端记录的能力，并要求创建请求幂等；这是对 03 阶段的扩展，相关接口与关联能力均待实施。01—03 的历史范围与验收记录保持不变。

## 目标与使用场景

用户在 Snippets 中保存本地片段后，可以主动将指定片段的标题和内容提交给 Java 后端。首次提交创建关联，后续手动更新同一条后端记录；本轮采用单条手动提交，不切换列表数据源。

Clipboard 和 Transform 本地运行，只有 Snippets 提供手动上云入口。启动、复制、另存为 Snippet、新增、编辑和保存均不自动上传。

“上云”沿用用户提出的按钮文案。目前目标服务为本机 `http://127.0.0.1:8080`，数据写入本机 Docker 中的 PostgreSQL，不能将结果描述为公网云端备份或跨设备同步。页面应提供简短说明：“保存到当前连接的后端服务”。

## 功能规则

### 入口与提交

- 每条已保存的本地 Snippet 的操作区增加“上云”按钮，沿用现有按钮样式和行内反馈方式。
- 点击仅提交该片段当前已保存的 `title` 和 `content`；未保存的表单内容不参与提交。
- 首次上云调用创建接口；成功后持久化后端 ID 和最近成功提交的标题、正文快照，与本地片段关联。后端生成独立的 UUID 和时间，不覆盖本地业务 ID、标题或正文。
- 已关联片段的内容变化后，按钮显示“更新到云端”，调用更新接口修改同一条后端记录；内容未变化时禁用再次提交。
- 上传和关联状态变化不修改本地 `createdAt`、`updatedAt`，不影响列表顺序。
- 按 Java 当前契约校验非空标题和内容，以及去除首尾空白后的标题长度不超过 255；不得静默截断本地内容。最终校验与响应以后端实际返回为准。

### 持久化状态

- “未上云”：尚未确认关联后端记录，包括从 Clipboard 另存的新片段和原有未关联片段。
- “已上云”：本地当前标题、正文与最近成功提交的快照一致。
- “有未上传修改”：已有后端关联，但本地当前标题或正文与最近成功提交的快照不同。
- 状态反映本地内容与最近成功提交结果的关系，不承诺实时检测后端变化。比较内容快照时使用与请求一致的标题规范化规则，正文不截断、不压缩排版。
- 关联、快照和待确认创建请求均持久化，重启后可以恢复。若本地内容改回最近成功提交的快照，则恢复为“已上云”。

### 请求状态与反馈

- 请求期间按钮显示“上云中…”或“更新中…”并禁用重复提交；同一片段的编辑、删除同时禁用，避免提交过程中改变目标。
- 设置有限请求超时；服务未启动、连接失败、超时或接口拒绝时，显示可理解的行内错误并恢复按钮。
- 首次创建收到 `201`，更新收到 `200`，且响应包含有效后端记录后，保存关联与成功快照并显示“已保存到后端”。状态尚未成功落盘时不宣告完成；必须保留可恢复的请求信息。
- 无论成功或失败，本地片段均保留，原有复制、搜索、新增、编辑和删除功能继续使用本地数据。

### 重复与数据边界

- 首次创建在发送 HTTP 请求前，持久化该次创建的唯一请求标识及提交快照。结果不确定时保留二者，提示“结果未确认，请手动重试”，不自动重试或生成新的创建标识。
- 用户手动重试同一次创建时使用原标识和原快照，即使应用已重启，也不得重复创建后端记录。若等待确认期间本地内容已修改，先重试并确认原快照的创建结果，再由用户手动更新当前内容。
- 同一片段关联后只手动更新，不再调用创建接口。不同本地片段即使标题、正文相同，也允许分别创建后端记录，不按正文全局去重。
- 更新结果不确定时保留原成功快照并提示手动重试；重复更新相同内容不得新增记录或刷新后端业务更新时间。
- 本地编辑不会自动更新后端。本地删除仅删除本地片段及其关联信息，不调用后端删除接口；已上传记录仍保留在后端。若创建结果尚未确认，删除确认提示后端可能已保存，删除本地不会撤回该请求。
- 后端记录不存在时显示明确错误，保留本地内容及关联，不静默创建替代记录。
- 不自动上传现有片段，不批量上传，不在应用启动或保存片段时隐式调用后端。
- 用户长期维护的本地片段必须保留；后续升级或接入后端不得沿用 02、03 早期“测试数据可废弃”的规则清空已有数据。

## 接口约定

| 操作 | 接口 | 请求与成功响应 |
|---|---|---|
| 首次上云 | `POST /api/snippets` | 请求体为 `title`、`content`，桌面端通过 `Idempotency-Key` 请求头携带持久化的创建请求标识；返回 `201` 和后端记录 |
| 手动更新 | `POST /api/snippets/{id}/update` | `id` 为已关联的后端 ID，完整提交 `title`、`content`；返回 `200` 和更新后的后端记录 |
| 查询 | 现有 `GET /api/snippets?keyword=` | 保留列表和关键词查询，用于核验保存结果，不替换本地列表 |

- 响应记录继续包含 `id`、`title`、`content`、`createdAt`、`updatedAt`。不将本地业务 ID 或本地时间写入后端业务字段。
- 创建的幂等标识与创建结果需要在后端持久化；并发相同请求、应用或后端重启后的重试均返回原创建结果，不依赖进程内缓存。
- 相同创建标识与相同提交内容返回原 `201` 结果；相同标识携带不同内容返回 `409`，不新增或修改片段。
- 为兼容 03 已有调用方式，不携带幂等请求头的创建请求继续按原契约处理；桌面端首次上云必须携带该请求头。
- 更新目标不存在返回 `404`，输入非法返回 `400`；错误沿用统一错误响应结构。
- 更新保留后端 `id` 和 `createdAt`，仅内容变化时刷新 `updatedAt`。重复提交相同更新内容不新增记录，也不刷新业务更新时间。
- 本期不新增后端删除接口，不把创建和更新合并为遇到未知 ID 就新增的行为。

## 技术约束

- 延续 `Vue → window.clipflow → preload / IPC → Electron 主进程` 的受控调用边界；HTTP 请求与错误转换由主进程承担。
- 主进程依据本地片段 ID 读取已保存内容并调用固定的本机服务地址；不向渲染层开放任意 URL 请求能力。
- 扩展 Java 创建接口并新增 POST 更新接口；前后端响应类型明确区分，不将后端单条响应直接替换为本地列表。
- 本地持久化增加可选的后端关联、成功内容快照及待确认创建请求信息；旧 JSON 缺少这些信息时按未上云读取，保留原有片段和业务字段。
- 后端以版本化迁移保存幂等标识与创建结果的关联，不清空已有业务数据；不得以标题、正文相同替代请求幂等判断。
- 不新增依赖，不修改 Clipboard 或 Transform 的存储与行为。

## 验收标准

1. 未启动 Java 服务时，桌面端和全部离线 Snippets 功能正常；点击上云得到明确错误，本地记录不丢失。
2. 首次上云创建记录后，通过 GET 查询到对应内容；应用重启后关联和“已上云”状态恢复，后端重启后数据仍存在。
3. 已关联片段本地修改后显示“有未上传修改”，点击手动更新后修改同一后端 ID，记录总数不增加，本地内容不被响应覆盖。
4. 内容未变化时禁用重复提交；内容恢复为最近成功快照时恢复“已上云”。重复更新相同内容不刷新后端业务更新时间。
5. 请求期间连续点击只发起一次请求，目标片段不能编辑、删除；成功、失败或超时后操作恢复。
6. 上传前后本地业务 ID、内容、时间和排序保持；更新关联信息不冒充本地编辑。读取旧 JSON、升级和恢复状态不丢失已有片段。
7. 模拟后端创建成功但响应丢失，应用或后端重启后手动重试原请求只保留一条后端记录；并发重试结果相同。相同标识携带不同内容返回 `409`；不同片段以不同标识提交相同内容可分别创建。
8. 待确认期间本地内容已改变时，先恢复原创建结果，之后再手动更新；不将不同内容发送给同一创建标识。
9. 超长标题、空白输入、后端 `400`、`404`、`409`、连接失败和结果不确定的超时均有明确反馈，无自动重试；`404` 不触发重新创建。
10. 本地删除不删除后端记录；本地编辑、启动、复制和另存均不自动上传，Clipboard 与 Transform 不调用后端。
11. 通过适当的桌面端测试及真实 PostgreSQL 集成测试验证关联恢复、创建幂等、更新和失败恢复，并完成现有测试和构建检查。
12. 记录实际验收系统；Windows、macOS 未实际验证的项目不标记完成。本需求中的新增能力均不得沿用 03 的历史验收结果标记完成。
