## 问题陈述

`Snippets` 目前只有 mock 列表和前端搜索壳子，用户无法保存、修改、删除或复制可复用文本；应用重启后也没有任何 Snippets 数据可恢复。对一个桌面效率工具而言，这使它无法承担“长期复用的模板和话术”这一产品职责。

当前迭代的目标是尽快交付一个可独立日常使用的离线 Snippets 闭环。Java 后端环境、账户、登录和跨设备同步尚未进入本次实施条件，因此不应阻塞本地功能落地，也不应以临时 mock 或散落的渲染层存储替代可维护的桌面端能力。

## 解决方案

在 Electron 主进程中建立一个本地 Snippets 服务，将片段数据持久化到用户数据目录中的独立 JSON 文件，并通过现有 `preload` 桥接向渲染层提供受控的查询和 CRUD 能力。Snippets 页面使用该桥接加载、搜索、创建、编辑、删除和复制片段，并在重启后恢复本地数据。

本次只交付离线单机体验。数据仅用于当前版本验证；未来后端版本可以直接废弃这些测试数据，不要求迁移、导入或同步。

## 用户故事

1. 作为桌面应用用户，我希望查看已保存的常用片段，以便快速找到可复用的文本。
2. 作为桌面应用用户，我希望片段按最近新建或编辑的顺序显示，以便最近维护的模板优先出现。
3. 作为桌面应用用户，我希望按标题或内容搜索片段，以便在片段数量增加后仍能快速定位目标。
4. 作为桌面应用用户，我希望搜索结果会随输入更新，以便无需切换页面即可缩小范围。
5. 作为桌面应用用户，我希望在没有匹配项时看到明确的空状态，以便知道当前没有可用结果。
6. 作为桌面应用用户，我希望新建片段时填写标题和内容，以便为文本建立可辨识的名称和可复制的正文。
7. 作为桌面应用用户，我希望标题和内容不能为空，以便列表中不会出现无法识别或无法复用的无效记录。
8. 作为桌面应用用户，我希望首尾空白不会被当作有效标题或内容，以便避免误存空白片段。
9. 作为桌面应用用户，我希望允许重复标题或重复内容，以便可以保留不同语境下的相似模板。
10. 作为桌面应用用户，我希望编辑已有片段，以便更新不再适用的模板内容。
11. 作为桌面应用用户，我希望编辑保存后该片段显示为最近更新，以便我能立即在列表顶部看到它。
12. 作为桌面应用用户，我希望删除片段前得到确认，以便避免误删不可恢复的本地内容。
13. 作为桌面应用用户，我希望确认删除后该片段立即从列表和本地存储中移除，以便完成清理。
14. 作为桌面应用用户，我希望取消删除时原片段保持不变，以便我能安全地放弃该操作。
15. 作为桌面应用用户，我希望一键把片段内容复制到系统剪贴板，以便可以粘贴到其他应用。
16. 作为桌面应用用户，我希望复制操作提供成功或失败的短暂行内反馈，以便知道操作是否完成。
17. 作为桌面应用用户，我希望关闭并重新打开应用后仍能看到已保存的片段，以便片段库可长期使用。
18. 作为桌面应用用户，我希望损坏或不存在的本地片段文件不会阻止应用启动，以便应用仍可恢复到可使用的空列表状态。
19. 作为桌面应用用户，我希望 Snippets 数据与剪贴板历史分开保存，以便清理或损坏一种数据不会影响另一种功能。
20. 作为未来的开发者，我希望渲染层只经受控桥接访问 Snippets，以便后续替换或增加数据来源时不会在 UI 中散落存储细节。

## 实施决策

- Snippets 是离线、单用户的桌面端功能；本次不连接 Java 后端、数据库或任何远端 API。
- 使用 Electron 主进程负责片段的读取、校验、写入、复制和本地 JSON 持久化，避免渲染组件直接读写 `localStorage` 或文件系统。
- 为 Snippets 使用独立的 `snippets.json` 用户数据文件，不与剪贴板历史混存。
- 将现有 `SnippetItem` 作为数据模型，包含 `id`、`title`、`content`、`createdAt` 和 `updatedAt`；不增加标签、分类、置顶、变量或快捷键字段。
- 新建和编辑共享同一套表单交互；保存时对标题和内容执行 trim 校验，二者均须为非空字符串。
- 允许重复标题和重复内容；本次没有长度上限或去重规则。
- 新建和编辑均刷新 `updatedAt`；复制不改变 `updatedAt`。列表统一以 `updatedAt` 倒序显示。
- 删除是不可恢复操作，必须经用户二次确认；本次不提供撤销、回收站或历史版本。
- 复制通过 Electron 系统剪贴板能力完成，并在 UI 中展示短暂的行内成功或失败状态。
- 本地文件不存在、格式不正确或无法解析时，服务应以空列表继续运行并记录可诊断错误；不得让整个应用因 Snippets 数据损坏而无法启动。
- `window.clipflow` 是渲染层与 Snippets 能力之间的主集成边界。渲染组件通过该桥接获取和变更片段，主进程服务隐藏 JSON 文件、系统剪贴板和持久化细节。
- 当前本地数据视为测试数据。未来接入后端时允许直接清空或废弃，且本 spec 不定义迁移、导入、合并或同步行为。

## 测试决策

- 测试应验证可观察行为，而不是服务内部数组、私有方法或具体 JSON 写入步骤。
- 主要自动化测试边界是 Snippets 主进程服务。它应覆盖：空文件初始化、有效数据恢复、损坏数据降级为空列表、创建、编辑、删除、标题或内容非法输入、排序、持久化，以及复制成功和失败的可观察结果。
- 通过现有 `preload` 桥接进行少量集成验证，确认渲染层能够加载数据并触发新增、编辑、删除和复制意图；避免让组件测试重复服务层已覆盖的规则。
- 手动验证应覆盖创建片段、搜索、编辑后排序变化、取消和确认删除、复制后粘贴到其他应用，以及重启应用后的恢复。
- 构建验证必须继续包含 TypeScript 检查和 Electron/Vite 生产构建。
- 现有代码库没有 Snippets 自动化测试先例；实施时引入的测试工具应能在 Node 环境中测试主进程服务，并保持测试隔离，不依赖真实用户数据目录。

## 非本次范围

- Java、Spring Boot、PostgreSQL、Docker 或任何后端 API。
- 登录、账户、用户隔离或权限控制。
- 游客与登录账户的数据切换。
- 多设备同步、离线队列、冲突解决、迁移、导入或导出。
- 云端备份或公开部署。
- 标签、分类、置顶、手动排序、变量替换、快捷键或全文搜索。
- 回收站、撤销或片段版本历史。
- 剪贴板历史的存储方式或既有行为调整。

## 进一步说明

本 spec 有意先让 Snippets 成为独立可用的离线功能，同时保持与现有 Electron 架构一致：主进程拥有系统与文件能力，`preload` 提供窄桥接，渲染层只负责交互和显示。

后续如需探索“游客本地、登录后使用后端”的产品模式，应新建 spec，并先明确数据所有权、切换时机、同步方向、冲突策略和隐私边界。不能把这些问题作为本次离线 CRUD 的隐含职责。
